# リーンプロダクト スターター

個人開発アプリのアイデアを「リーンプロダクト × バンディット戦略」の観点で整理するワークフロー。

## ファイル責務

| ファイル | 責務 | 更新タイミング |
|--------|------|-------------|
| **SKILL.md**（このファイル） | 実行ワークフロー（4 Step）・必須出力項目・チェックリスト | ワークフロー変更時 |
| **references/lean-product-guide.md** | 詳細理論・KPI業界目安・コピペ用テンプレート | 理論・数値・事例の更新時 |

> 詳細理論・KPI業界目安・コピペテンプレートは `references/lean-product-guide.md` を参照。
> SKILL.md の出力例はあくまでワークフロー説明用の最小例であり、正式テンプレートは reference 側が source of truth。

---

## Step 1: アイデアのヒアリング

以下の2項目が**両方揃っているか**を確認する。引数で与えられていても、揃っていない場合は AskUserQuestion で補完してから Step 2 に進む。

| 必須項目 | 内容 |
|---------|------|
| 作りたいもの | どんなアプリか（一文で） |
| 誰が困っているか | 想定ユーザーと、その人が今どんな不便を抱えているか（具体シーン） |

**両方揃っている場合**: Step 2 へ進む（追加質問不要）。

**どちらか欠けている場合**: AskUserQuestion を使い、1回の質問で両方をまとめてヒアリングする。

**絞り込みのポイント**: 「みんなが使える」という答えが返ってきたら、「一番最初に使ってもらいたい人は誰ですか？」と絞り込む。

## Step 2: 7セクションで整理して出力する

以下の7セクションを順番に埋めて、マークダウン形式で出力する。
抽象的な回答は避け、ユーザーのアイデアに即した具体的な言葉で書く。

### 【1】誰の・何の痛みか

ターゲットと痛みを1つに絞る。痛みは3分類のどれかに当てはめる：

- **廃棄ロス系**: 使わずに捨てることへの後悔・損失
- **意思決定系**: 何を選ぶか判断できずに時間を浪費する
- **ムダ買い系**: 必要のないものにお金を払ってしまう

```
出力例:
- ターゲット: 一人暮らしの社会人（20〜30代）
- 痛み: 冷蔵庫の食材を把握できずに食品を廃棄してしまう（廃棄ロス系）
- 具体シーン: 「買い物してきたら同じ食材がすでにあった」「賞味期限切れに気づかず捨てる」
```

### 【2】MVP設計

**使った瞬間に得を感じられる出力**を最短で実現する設計。
「入れない機能」を明記することが重要。

```
出力例:
- 最初の価値: レシートを撮るだけで食材リストが作られ、今夜使えるものが分かる
- 入れる機能: レシートOCR、食材リスト表示、賞味期限アラート
- 入れない機能: レシピ提案、栄養分析、家族共有、購入履歴分析
```

### 【3】コアリスクの特定

このアプリが成立するための前提技術・仮定のリスクを特定し、検証基準（数値）を決める。

```
出力例:
- リスク1（技術）: OCRの精度がレシートで85%以上出るか
  → 検証基準: 30枚のレシートでOCR精度85%以上
- リスク2（行動）: ユーザーがレシートを撮影する習慣が続くか
  → 検証基準: 初回インストール後7日間で3回以上撮影
```

### 【4】成功判定基準

数値で先に決める。「なんとなくうまくいった」は成功ではない。

| 指標 | 目標値 | 計測方法 |
|------|--------|---------|
| 7日継続率 | 40%以上 | インストール後7日目の起動有無 |
| 週起動回数 | 3回以上 | アプリ起動イベント |
| コア機能利用率 | 60%以上 | レシート撮影イベント/週 |

```
出力例（食費記録アプリ）:
- 7日継続率 ≥ 40%
- 週3回以上のレシート撮影
- 食品廃棄が「減った」とユーザーが答える率 ≥ 60%
```

### 【5】フィードバック収集SOP

検証仮説・計測イベント・失敗の定義を事前定義する。

```
出力例:
- 検証仮説: 「レシートを撮るだけで食材が記録できれば、廃棄が減る」
- 計測イベント: 起動、レシート撮影、食材確認、廃棄報告
- 成功の定義: 7日継続率40%かつ週3回撮影
- 失敗の定義: 7日後にアクティブユーザーが20%未満
- 収集方法: アプリ内ログ + 7日後のプッシュアンケート（3問以内）
```

### 【6】次の賭け（バンディット戦略）

**今はやらない。** 手応えが出たら試す次の一手を複数案で用意しておく。
「成功判定基準を満たしたとき」だけ実行する。

```
出力例:
- 案A: レシピ提案機能（今ある食材から料理を提案）
- 案B: 近くのスーパーの特売情報と連携
- 案C: 食費の月次サマリーとグラフ表示
→ どれを試すかは手応え（ユーザー要望の多さ）で決める
```

### 【7】競合分析

なぜ競合が普及していないかの仮説＋差別化ポイント。

```
出力例:
- 主な競合: 家計簿アプリ（マネーフォワード、Zaim）
- 普及していない理由の仮説: 記録が面倒（入力コストが高い）、食品廃棄ではなく支出管理が目的
- 差別化: 「撮るだけ」で食材管理に特化、廃棄削減にフォーカス
```

## Step 3: リーンチェック

7セクションを埋めた後、以下の5項目を確認する。
問題があれば指摘し、修正案を提示する。

| チェック項目 | 確認 |
|------------|------|
| ターゲットが「全員」「みんな」になっていないか | ✓/要修正 |
| MVPに入れない機能を明示しているか | ✓/要修正 |
| 成功判定基準が具体的な数値になっているか | ✓/要修正 |
| コアリスクを1つ以上特定し、検証基準があるか | ✓/要修正 |
| 競合が普及していない理由の仮説があるか | ✓/要修正 |

---

## Step 4: 今週中の具体アクション3つを提案

整理した内容をもとに、**今週中にできる**具体的な次のアクションを3つ提案する。

アクションの優先順位：
1. コアリスクの検証（技術的な不確実性を先に潰す）
2. ターゲットユーザーへのインタビュー（痛みの深さを確認）
3. 最小プロトタイプの着手（動かして仮説を試す）

```
出力例:
1. レシートOCRの精度テスト: Google Vision API か Tesseract で30枚のレシートを試す
2. インタビュー: 一人暮らしの友人2〜3人に「食材廃棄の頻度と理由」を5分ヒアリング
3. ペーパープロトタイプ: 画面設計をFigmaかノートに書いて、ユーザーに見せてフィードバックをもらう
```

---

## 出力フォーマット

- マークダウン形式で7セクション＋リーンチェック＋アクション3つを出力する
- 各セクションは具体例を交えて記述する（「TBD」「要検討」は使わない）
- ユーザーのアイデアに即した言葉で書く（汎用的な表現は避ける）
