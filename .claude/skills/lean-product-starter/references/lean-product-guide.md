## 1. バンディット戦略の核心思想

### 「作って試す」ではなく「賭けを管理する」

バンディット戦略の本質は、**不確実性の高い賭けをコントロールしながら学習を積み重ねる**手法。
カジノのスロットマシン（バンディット）に少額を入れて試しながら勝率の高いマシンを見つける行動に由来する。

### 個人開発への適用

```
賭けの管理フロー:
1. 仮説を立てる（このアプリはこういう人に刺さるはず）
2. 最小のコストで試す（MVPを作って検証）
3. 手応えを数値で評価（成功判定基準を事前に定義）
4. 手応えがあれば次の賭けに進む
5. 手応えがなければピボットか中止を判断する
```

### 重要な原則

- **成功の定義を先に決める**: 試した後で「まあよかった」は失敗
- **手応えの前に次を作らない**: 今の仮説が正しいかを確認してから次へ
- **「全部入り」で出発しない**: 最初の賭けは最小単位で

### 探索と活用のバランス

バンディット戦略の核心は「探索（exploration）と活用（exploitation）のバランス」にある。

- **探索**: まだ試していない選択肢を試す（どれが勝つかを学ぶ）
- **活用**: 今のところ成果が良い選択肢に集中する（成果を最大化する）

| バランスが崩れると | 結果 |
|----------------|------|
| 探索しなさすぎる | 最初に少し良かった案に全振りし、もっと良い案を見落とす |
| 活用しなさすぎる | ずっと均等に試し続け、学習は進んでも成果が出ない |

**実務的な運用ルール**（厳密な数式不要）:
```
- 最初は複数案を小さく試す（広めに探索）
- 手応えが見えてきたら有望な案に資源の50〜70%を寄せる
- 完全固定せず、他の案にも一定量を残す（探索を完全にはやめない）
- 2〜3回連続で弱い案は止める（中止基準を事前に決める）
```

### ベイズ更新：仮説を観測で更新する

最初の仮説は「仮の出発点」にすぎない。実験結果ごとに確からしさを更新していく。

```
ベイズ更新フロー:
1. 最初の仮説を置く（「たぶんAが有望そう」程度でよい）
2. 小さく試して結果を得る
3. 結果に応じて有望度を更新する（「Aは初回が強いが継続が弱い」等）
4. 更新後の見立てに基づいて次の配分を決める
```

**重要**: 更新は「勝ち負けの二択」ではなく「解像度を上げること」。弱かった案からも「どのユーザーには刺さるか」「どの条件では効くか」を学べる。

## 2. 痛みの3分類 詳細

ユーザーの「痛み」を3つに分類することで、MVPの価値がクリアになる。

### 廃棄ロス系

**定義**: 使わずに捨てることへの後悔・損失感

| 具体例 | 典型的なシーン |
|--------|--------------|
| 食品廃棄 | 賞味期限切れに気づかず捨てる |
| 未消化コンテンツ | 読まずに積んだ本・見ていないサブスク |
| 未使用サービス | ジム会費を払いつつ行かない |
| 期限切れクーポン | 使えたはずのポイントが消える |

**MVPのポイント**: 廃棄が起きる「直前」に通知・気づきを与える仕組みを最短で

### 意思決定系

**定義**: 何を選ぶか判断できずに時間・エネルギーを浪費する

| 具体例 | 典型的なシーン |
|--------|--------------|
| 食事の選択 | 「今日何食べよう」で15分悩む |
| 購入判断 | レビューを読みすぎて買えない |
| タスク優先順位 | 何から手をつけるか分からず止まる |
| 情報過多 | ニュース・通知が多すぎて重要なものを見落とす |

**MVPのポイント**: 「1つの答えを出す」ことに特化。選択肢を増やすのは後

### ムダ買い系

**定義**: 必要のないものにお金を払ってしまう

| 具体例 | 典型的なシーン |
|--------|--------------|
| 衝動買い | セールで不要なものを買う |
| 重複購入 | 家にあるものをまた買う |
| 過剰サブスク | 使っていないサービスを解約し忘れる |
| 見栄え買い | 実際には使わないものを「いつか使うかも」で購入 |

**MVPのポイント**: 「今持っているもの」を可視化し、購入前に確認できる仕組み

## 3. MVP設計の原則と失敗パターン

### 設計の基本原則

**「使った瞬間に得を感じられる」を1機能で実現する**

```
良いMVP設計の問い:
- アプリを開いて30秒以内に価値を感じられるか？
- 「また使いたい」と思う出力が出るか？
- 機能を外したとき、まだ価値があるか？
```

### 機能の取捨選択基準

| 機能 | 含める基準 |
|------|-----------|
| コア機能 | コアリスクの解消に直結する（必ず含める） |
| 補助機能 | コア機能の体験を補う（MVP後に検討） |
| 周辺機能 | 別のユーザーニーズに応える（ロードマップ） |

### 典型的な失敗パターン

**失敗1: 機能盛りすぎ**
「これもあったら便利」を追加し続けた結果、いつまでもリリースできない。
→ 対策: 「入れない機能リスト」を先に作る

**失敗2: 自分のほしいものを作る**
自分が使いたいからという理由で機能を追加し、ターゲットユーザーと乖離する。
→ 対策: 機能追加ごとに「これはどのターゲットの痛みを解消するか」を確認

**失敗3: UXより機能を優先**
機能はあるが使いにくいため誰も使わない。
→ 対策: 「ユーザーが最初にやること」を1つだけ完璧にする

**失敗4: バックエンドから作る**
データモデル・API設計から始め、フロントが最後になる。
→ 対策: 「ユーザーが見る画面」からプロトタイプを始める

## 4. コアリスクの特定と検証基準の決め方

### リスクの種類

| リスク種別 | 定義 | 例 |
|-----------|------|---|
| 技術リスク | 使おうとしている技術が想定通り動くか | OCR精度・API制限・処理速度 |
| 行動リスク | ユーザーが想定通り使うか | 入力習慣・継続利用・シーン想定 |
| 市場リスク | 想定したターゲットが実在するか | ペルソナの実在性・規模 |
| 競合リスク | 競合がすでに解決していないか | 既存サービスの代替可能性 |

### 検証基準の作り方

**悪い例**: 「OCRが使えるか確認する」
**良い例**: 「30枚の実際のレシートで試し、食品名の認識精度が85%以上」

```
検証基準の3要素:
1. 何を測るか（指標）
2. どんな条件で（サンプル・環境）
3. 合格ラインはどこか（数値）
```

### 検証の優先順位

最初に解消すべきは「アプリ自体が成立しないリスク」。

1. **技術リスク**: 作れないなら全部無意味
2. **行動リスク**: 誰も使わないなら意味がない
3. **市場リスク**: ユーザーがいないなら広がらない
4. **競合リスク**: 代替されるなら差別化が必要

## 5. 成功判定基準の設計（KPI一覧・業界目安）

### 個人開発アプリの代表的KPI

| 指標 | 定義 | 個人開発の目安 |
|------|------|--------------|
| 7日継続率 | インストール後7日目も利用しているユーザー比率 | 30〜40%で及第点 |
| 30日継続率 | 30日後も利用しているユーザー比率 | 15〜25%が目安 |
| 週起動回数 | 1ユーザーが週に何回アプリを開くか | ユーティリティ系は3回以上 |
| コア機能利用率 | 中核機能を使うユーザーの割合 | 60%以上が理想 |
| セッション時間 | 1回の利用時間 | 目的による（記録系は短い方が良い） |

### KPIの設定原則

**原則1: ユーザーの行動を測る（感想ではなく）**
```
悪い: 「ユーザーが満足している」
良い: 「7日後も週3回以上起動している」
```

**原則2: コアバリューに紐づく指標を選ぶ**
食材管理アプリなら「食品廃棄が減ったか」を直接測る仕組みを作る。

**原則3: 1〜3指標に絞る**
最初は多くの指標を追わない。1つ改善してから次を測る。

### フェーズ別の指標の変え方

| フェーズ | 重視する指標 |
|---------|------------|
| MVP検証（〜100ユーザー） | 7日継続率・コア機能利用率 |
| グロース（100〜1000ユーザー） | 紹介率・口コミ流入 |
| スケール（1000+ユーザー） | LTV・チャーン率 |

## 6. フィードバック収集SOPの実践

### 事前定義の重要性

「うまくいったかどうか」を試した後に決めると、人間はポジティブバイアスで判断を誤る。
失敗の定義を事前に書いておくことで、撤退・ピボットの判断ができる。

### 計測イベントの設計

**記録するべきイベント（最小セット）**:
```
- app_open: アプリ起動
- core_feature_use: コア機能の実行（レシート撮影、タスク追加など）
- return_visit: 翌日以降の起動
- error_encountered: エラー発生（どこで詰まるかを把握）
```

### ユーザーインタビューのタイミング

| タイミング | 目的 | 質問例 |
|-----------|------|-------|
| MVP前 | 痛みの深さを確認 | 「今、どうやってこの問題を解決していますか？」 |
| MVP後7日 | 体験の確認 | 「使ってみて、何が一番役に立ちましたか？」 |
| MVP後30日 | 継続の理由を把握 | 「続けて使っている理由は何ですか？」 |

### インタビューの5つのNG質問

1. 「このアプリ、いいと思いますか？」→ 社交辞令で「いい」と言う
2. 「この機能があったら使いますか？」→ 「使う」と言うが実際には使わない
3. 「何が欲しいですか？」→ 解決策ではなく、現在の行動を聞く
4. 「なぜ使わなかったのですか？」→ 使わなかった事実を確認してから聞く
5. 「どんな改善がしたいですか？」→ 具体的なシーンから聞く

## 7. 次の賭け・共通モジュール設計

### バンディット戦略での「次の賭け」の管理

**重要な原則**: 次の賭けは「今の仮説が成立した後」にだけ実行する。

```
賭けの管理表（例）:
| 案 | 仮説 | 成功指標 | 優先度 |
|----|------|---------|-------|
| レシピ提案 | 食材があれば料理のアイデアが欲しい | 1週間に2回以上タップ | A |
| 特売連携 | 安い日に買い物したい | DAU向上20% | B |
| 家族共有 | 夫婦で管理したい | 2人以上利用が30% | C |
```

### ピボットの判断基準

成功判定基準を満たせなかった場合の判断フレーム:

1. **ターゲットが間違っていたか?** → ターゲット変更
2. **痛みの解決策が間違っていたか?** → 機能ピボット
3. **チャネルが間違っていたか?** → 配布方法変更
4. **痛み自体がなかったか?** → アイデア全体を見直し

### 中止基準と継続条件

「成功したら次へ」だけでなく、**失敗したときの撤退ライン**を事前に決めておく。

```
中止基準（撤退・保留に移行する条件）:
- 7日継続率が目標の半分以下（例: 目標40% → 実績20%未満）
- 2〜3週間の計測で改善傾向がゼロ
- コア機能の利用率が10%未満（誰もコア機能を使っていない）

継続条件（投資を増やす条件）:
- 成功判定基準を2週連続でクリア
- ユーザーから「毎日使っている」「友人に勧めた」という声が出る
- 計測指標が明確な上昇トレンドを示している
```

**アンチパターン**: 成功基準なしのまま数ヶ月続けると、ポジティブバイアスで「なんとなく良さそう」と判断してしまう。中止基準は事前に書いておくことで機能する。

## 8. 競合分析の実践方法

### なぜ競合が普及していないかを分析する

既存の競合アプリが普及していない理由を先に分析することで、差別化ポイントが明確になる。

### 競合分析フレーム

```
競合アプリ: ○○アプリ
- 機能: [主要機能を3つ]
- ユーザーレビューの不満点: [App Storeレビューから抜粋]
- 普及していない仮説: [なぜ広まらないか]
- 自分の差別化: [この仮説を覆す方法]
```

### 情報収集の手順

1. **App Storeのレビューを読む**: 星2〜3のレビューに本音がある
2. **使ってみる**: 実際に1週間使ってみて離脱ポイントを探す
3. **SNSで検索する**: 「アプリ名 不満」「アプリ名 使いにくい」で検索
4. **競合ユーザーにインタビューする**: なぜ使い続けているか・やめた理由を聞く

### 差別化の方向性

| 方向性 | 定義 | 例 |
|--------|------|---|
| シンプル化 | 競合より圧倒的に使いやすくする | 入力ステップを1/3にする |
| 特化 | 特定のニッチに深く刺さる | 一人暮らし専用に絞る |
| 統合 | 複数ツールを1つに | 家計管理と食材管理を連携 |
| 体験 | UXで圧倒する | アプリを開く動作自体を楽しくする |

## 9. 個人開発のアンチパターン9選

### AP1: 「全員が使える」ターゲット設定

「主婦から学生まで」は誰にも刺さらない。
→ 最初の100ユーザーが誰かを具体的に書く

### AP2: 「いつか使う」機能の先行開発

バックグラウンドで動く分析機能・高度な設定画面など、MVPに不要な機能に時間を使う。
→ コアバリューを1つ決めてそれだけを完璧にする

### AP3: 成功基準なしのリリース

「とりあえず出してみる」→ 誰も使わないがどう判断すればよいか分からない。
→ 成功/失敗の数値を出す前に決める

### AP4: 競合を調べない

「こんなアプリはない」と思って作ったら似たものがすでにある。
→ App Store検索・Google検索を30分以上やってから設計する

### AP5: コアリスクを後回しにする

UI設計・ランディングページから作り始め、「実は技術的に無理」と後から気づく。
→ 最初にコアリスクを潰す PoC を作る

### AP6: ユーザーの声を聞かずに作り続ける

「これは絶対に良い」と思い込んで、実際のユーザーに見せない。
→ 最低5人にプロトタイプを見せてから本開発に入る

### AP7: 完璧を目指して出さない

「もう少し磨いてから」を繰り返してリリースが半年後になる。
→ 「今すぐ出せる最小版」を定義して期限を決める

### AP8: 1つのアプリに賭けすぎる

1年かけて作ったアプリが全くバズらないと心が折れる。
→ 1〜2ヶ月で検証できる規模に抑える

### AP9: 数字を見ない

ダウンロード数だけ見てDAU・継続率を確認しない。
→ Firebase Analytics や Mixpanel で最低限の計測を初日から入れる

### AP10: 一度勝った案がずっと勝つと思い込む

「先週効いた機能は来月も効く」と思い込み、探索を止める。
→ ユーザー層や利用シーンが変わると有効な選択肢も変わる。定期的に新案と比較する

### AP11: 初期仮説に感情移入する

「自分が考えた案だから」という理由でデータより感情を優先し、仮説の更新が止まる。
→ 仮説はあくまで「仮の出発点」。外しながら当たりに近づくのが戦略の本質
