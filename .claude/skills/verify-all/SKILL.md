# 検証スキル

テスト・ビルド確認から総合検証まで対応する。まず検証範囲を確認し、適切なフローを実行する。

## ステップ0: 検証範囲の確認

ユーザーの呼び出しキーワードから検証モードを判断する。判断できない場合は AskUserQuestion で確認する。

| キーワード | モード |
|-----------|--------|
| 「テスト」「ビルド」「動作確認」「軽量」 | **軽量検証**（Phase 1 のみ） |
| 「総合」「全部」「統合テスト」「手動テスト」「リリース前」 | **総合検証**（Phase 1〜4 すべて） |

---

## Phase 1: 自動テスト・ビルド確認（軽量検証・総合検証 共通）

### 1-1. 単体テスト実行

```bash
npm test
```

- 全テストがパスするまで修正を繰り返す
- 失敗したテストの原因を分析し、テストコードまたは実装コードを修正する
- 修正後は再度 `npm test` で全件パスを確認する

### 1-2. ビルド確認

```bash
npm run build
```

- ビルドエラーがあれば原因を特定し修正する
- 型エラー、import漏れ、未使用変数などに注意する
- 修正後は再度ビルドを実行して成功を確認する

### Phase 1 完了条件

- [ ] `npm test` が全件パス
- [ ] `npm run build` が成功

> **軽量検証モードの場合はここで完了。** 結果をユーザーに報告する。

## Phase 2: API統合テスト（総合検証のみ）

変更に関連するAPIエンドポイントに対して、開発サーバー上でリクエストを送信し動作を確認する。

### 2-1. 変更の影響範囲を特定

```bash
git diff --name-only origin/main...HEAD
```

- 変更されたファイルから影響を受けるAPIルートを特定する
- `app/api/` 配下の変更は直接テスト対象
- `lib/` 配下の変更はそれを利用するAPIルートもテスト対象

### 2-2. 開発サーバーの起動確認

```bash
# 開発サーバーが起動していない場合、別ターミナルで起動
npm run dev
```

サーバーが `http://localhost:3000` で応答することを確認する。

### 2-3. APIエンドポイントテスト

影響を受ける各APIエンドポイントに対してリクエストを送信する。

**テスト観点:**

| 観点 | 確認内容 |
|------|----------|
| 正常系 | 期待通りのレスポンス（ステータスコード、レスポンスボディ） |
| 認証 | 認証なしリクエストで401が返ること |
| 認可 | 他ユーザーのリソースアクセスで403が返ること |
| バリデーション | 不正な入力で適切なエラーレスポンスが返ること |
| エラーハンドリング | エラー時に内部情報が漏洩していないこと |

**テストコマンド例（PowerShell）:**

```powershell
# 認証なしで401を確認
Invoke-RestMethod -Method GET -Uri "http://localhost:3000/api/inventories" -ErrorAction Stop

# 認証ありリクエスト（Firebaseトークンが必要な場合はブラウザから取得）
$headers = @{ "Authorization" = "Bearer $token" }
Invoke-RestMethod -Method GET -Uri "http://localhost:3000/api/inventories" -Headers $headers

# エラーレスポンスの内容確認（内部情報漏洩がないか）
try {
    Invoke-RestMethod -Method GET -Uri "http://localhost:3000/api/inventories/invalid-id" -Headers $headers
} catch {
    $_.Exception.Response
}
```

**テストコマンド例（curl / bash環境）:**

```bash
# 認証なしで401を確認
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/api/inventories

# エラーレスポンスの内容確認
curl -s http://localhost:3000/api/inventories/invalid-id -H "Authorization: Bearer $TOKEN"
```

### 2-4. テスト結果の記録

各APIテストの結果をまとめる。失敗があれば原因を特定し修正する。

## Phase 3: 手動テスト手順書の生成（総合検証のみ）

変更に応じた手動テスト手順書を `docs/manual-testing/` に生成する。

### 3-1. 手順書の作成

変更内容を分析し、以下のテンプレートに基づいて手動テスト手順書を作成する。

**出力先:** `docs/manual-testing/<機能名>.md`

**テンプレート構成:**

```markdown
# <機能名> 手動テスト手順書

作成日: YYYY-MM-DD
対象イシュー: #XX（該当する場合）
対象ブランチ: <ブランチ名>

## 前提条件
- [ ] 開発サーバーが起動していること (`npm run dev`)
- [ ] ブラウザでログイン済みであること
- [ ] テスト用データが準備されていること（必要な場合）

## テストケース

### TC-01: <テストケース名>
**目的:** <何を確認するか>
**前提:** <テスト前の状態>
**手順:**
1. <操作1>
2. <操作2>
3. <操作3>
**期待結果:** <期待される動作>
**確認方法:** <画面のどこを見るか、DevToolsの確認など>

### TC-02: ...

## 異常系テスト

### TC-E01: <異常系テストケース名>
**目的:** <何を確認するか>
**手順:**
1. <操作>
**期待結果:** <エラーメッセージ、フォールバック動作など>

## ブラウザDevToolsでの確認項目
- [ ] Networkタブ: APIリクエストのステータスコードが正しいこと
- [ ] Consoleタブ: エラーが出力されていないこと
- [ ] Applicationタブ: 認証トークンが正しく付与されていること

## テスト結果記録

| TC | 結果 | 確認者 | 日時 | 備考 |
|----|------|--------|------|------|
| TC-01 | - | - | - | - |
| TC-02 | - | - | - | - |
```

### 3-2. 手順書の内容基準

手順書に含めるべきテストケースの種類:

| 変更種別 | 必須テストケース |
|----------|-----------------|
| 新規APIエンドポイント | 正常系、認証確認、バリデーション、エラーハンドリング |
| 既存API修正 | 修正箇所の正常系、回帰テスト（既存機能が壊れていないこと） |
| UI変更 | 画面表示確認、操作フロー、レスポンシブ対応 |
| セキュリティ修正 | 脆弱性が再現しないこと、正常系への影響なし |
| ビジネスロジック変更 | 境界値テスト、計算結果の確認、関連機能への影響 |

### 3-3. 機能別テスト観点リファレンス

以下はこのプロジェクト固有の機能に対するテスト観点:

**レシート解析 (`/input`):**
- レシート画像のアップロードと解析結果の表示
- 解析結果のプレビュー画面での食材名・数量・単位の確認
- 在庫への一括登録が正常に完了すること
- 不正な画像（レシート以外）を送信した場合のエラー表示

**在庫管理 (`/inventory`):**
- 在庫一覧の表示（自分の在庫のみ表示されること）
- 消費ボタン(-1)で数量が減少すること
- 数量0で自動削除されること
- 編集モーダルでの数量・期限の変更
- 削除操作と確認ダイアログ

**AIチャット (`/chat`):**
- チャットメッセージの送受信
- 在庫情報に基づいた回答が得られること
- レシピページからの遷移時に初期メッセージが設定されること

**通知 (`/notifications`):**
- 通知一覧の表示
- 既読/未読の状態管理
- レシピモーダルの表示と調理確認

**認証:**
- 未ログイン状態でのリダイレクト
- ログイン/ログアウトの動作
- トークン期限切れ時の挙動
