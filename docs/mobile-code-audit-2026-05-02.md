## P0/P1: 先に直すべき不具合・未実装

### 1. ミッション初期化/リセットでミッションが消える可能性がある

**問題点**

`app/_layout.tsx` で `resetDailyMissions()` / `resetWeeklyMissions()` を実行した後、リセット前に取得した `missions` を見て生成判定しています。前日や前週のミッションが残っている状態で起動すると、リセットで `daily` / `weekly` が空になった後でも、古い `missions` を基準に「生成不要」と判定される可能性があります。

**修正方針**

- リセットと生成を1つの store action にまとめる。
- もしくは `resetDailyMissions()` / `resetWeeklyMissions()` が空にするだけでなく、必要ならその場で新しいミッションを生成する。
- `useEffect` 内では stale な `missions` を参照せず、`getState()` 相当の最新 state を基準に判定する。

**修正後の状態**

- 日付や週が変わった後にアプリを起動しても、ミッションが空のままにならない。
- ミッション画面の「ミッションがありません」が不必要に表示されなくなる。
- リセット処理の責務が明確になり、今後のミッション追加時も壊れにくくなる。

**関連ファイル**

- `mobile/app/_layout.tsx`
- `mobile/src/store/useAppStore.ts`

### 2. ミッション進捗更新で Zustand state を直接変更している

**問題点**

`updateMissionProgress` と `claimMissionReward` は、`missions` を shallow copy した後に、内部の mission object や `completedHistory` を直接変更しています。Zustand では外側の参照が変われば再描画される場合がありますが、ネストした state の直接変更は永続化、購読、デバッグ、将来の selector 最適化で不具合の原因になります。

**修正方針**

- `daily` / `weekly` の各 mission object も immutable にコピーして更新する。
- `completedHistory.push(...)` ではなく、新しい配列を作る。
- 更新ロジックを `updateMissionMap` のような小さい helper に切り出し、日次/週次で同じルールを使う。

**修正後の状態**

- ミッション進捗、報酬受け取り、履歴保存が安定する。
- state 更新の追跡がしやすくなり、将来のバグ調査が簡単になる。
- Zustand の永続化と再描画の整合性が上がる。

**関連ファイル**

- `mobile/src/store/useAppStore.ts`

### 3. バッジ判定に明確なロジック不備がある

**問題点**

`consecutive_days` の判定が、支出または自炊記録が1件でもあれば達成扱いになっています。そのため「7日連続記録」のバッジが、実際には連続していなくても獲得される可能性があります。

また、`monthly_goal_achieved` は `25000`、`15000`、`20` の固定値を見ています。現在は設定画面でスーパー予算とお小遣い予算を変更できるため、設定値とバッジ判定が一致していません。

**修正方針**

- `consecutive_days` は日付単位で記録有無を集計し、連続日数を計算する。
- `monthly_goal_achieved` は `goals.monthlyExpenseGoal`、`goals.allowanceGoal`、`goals.cookingGoal` を参照する。
- バッジ要件の意味を UI 文言と store 判定で揃える。

**修正後の状態**

- バッジ獲得条件が表示内容と一致する。
- ユーザーが設定した予算に沿って、目標達成バッジが判定される。
- 獲得済みバッジへの信頼性が上がる。

**関連ファイル**

- `mobile/src/store/useAppStore.ts`
- `mobile/app/(tabs)/badges.tsx`

### 4. 節約記録・無駄遣いなし・間食なし機能が UI から使えない

**問題点**

store には `addSavingsRecord`、`recordNoWasteDay`、`recordSnackFreeDay` が存在しますが、画面側から呼び出されていません。ホーム画面には連続日数が表示されますが、ユーザーが連続記録を増やす導線がないため、実質未実装です。

**修正方針**

- ホーム画面の「今日のアクション」に、節約記録や無駄遣いなし記録の導線を追加する。
- 間食なしは食費入力の `meal === 'snack'` と連動するのか、ユーザーが手動で記録するのかを仕様として決める。
- 使わない機能なら、store から削除するか UI から非表示にして状態表示も消す。

**修正後の状態**

- ホーム画面の連続日数が実際のユーザー操作で更新される。
- 節約記録、ミッション、バッジ、ポイントの流れがつながる。
- 「表示されているが使えない機能」が減る。

### 5. 設定画面の通知スイッチが見た目だけになっている

**問題点**

設定画面に「デイリー通知」「ミッション通知」のスイッチがありますが、現在は local state の切り替えだけです。AsyncStorage への保存も、`expo-notifications` などを使った実通知もありません。ユーザーには通知が有効になったように見えるため、期待と実動作がズレます。

**修正方針**

- 通知を実装する場合は、通知権限、通知スケジュール、設定値の永続化を追加する。
- まだ実装しない場合は、スイッチを削除するか「準備中」表示に変更する。
- 実通知を入れる場合は、オン/オフ変更時に既存スケジュールをキャンセル・再登録する。

**修正後の状態**

- 設定画面のスイッチと実際の通知動作が一致する。
- ユーザーが「オンにしたのに通知が来ない」と感じる問題を防げる。
- 通知未実装のままでも、UI 上の誤解を減らせる。

### 6. 自炊記録モーダルの日付が前回選択のまま残る可能性がある

**問題点**

`CookingModal` の `date` は `useState(getCurrentDate())` で初期化されますが、モーダルを閉じてもコンポーネント自体は再マウントされません。過去日を選んで閉じた後、次回もその日付のまま表示される可能性があります。

**修正方針**

- `visible` が `true` になったタイミングで `date` を今日に戻す。
- もしくは親側で `key` を変えてモーダルを再マウントする。
- `meal` も選択日付に応じた未記録の食事時間帯へ再初期化する。

**修正後の状態**

- 自炊記録を開いた時に、基本は今日の日付で始まる。
- 過去日の記録後に、次の記録を誤って過去日に保存する事故を防げる。
- 食事時間帯の初期選択も選択日付と整合する。

**関連ファイル**

- `mobile/src/components/CookingModal.tsx`

### 7. 支出金額入力が `parseInt` のため不正な文字列を通す可能性がある

**問題点**

支出入力では `parseInt(amount, 10)` を使っています。JavaScript の `parseInt` は `100abc` のような文字列を `100` と解釈するため、数字以外を含む入力が保存される可能性があります。

**修正方針**

- 予算入力と同じように、`/^\d+$/` で正の整数のみを許可する。
- `Number.isSafeInteger` も併用し、極端に大きい値を防ぐ。
- 入力中に数字以外を除去するか、保存時に明確なエラーを出す。

**修正後の状態**

- 支出金額に不正な文字列が混ざらない。
- 予算設定と食費入力のバリデーションルールが揃う。
- CSVや統計の計算結果が不正入力で壊れにくくなる。

**関連ファイル**

- `mobile/src/components/InputModal.tsx`

### 8. 統計の日別推移が時間間隔として誤解されやすい

**問題点**

統計画面では、月初・月末・支出がある日だけを `LineChart` に渡しています。一方、`LineChart` は渡された点を等間隔に描画します。そのため、例えば 5/1、5/20、5/31 が同じ間隔で表示され、実際の日付間隔と違って見えます。

**修正方針**

- 日別推移は全日付を渡して、31日分を正しい間隔で描画する。
- 小さい画面では横スクロールの棒グラフ、または週単位の集計グラフにする。
- 折れ線を維持する場合は、点の `x` 座標を日付番号に基づいて計算する。

**修正後の状態**

- 支出が発生した日と日付間隔が正しく読める。
- 「いつ増えたか」が誤解されにくくなる。
- 家計簿としての分析精度が上がる。

**関連ファイル**

- `mobile/app/(tabs)/stats.tsx`
- `mobile/src/components/LineChart.tsx`

## P2: 機能整合性・データ整合性の改善

### 9. 支出編集・削除時にミッションやバッジが再計算されない

**問題点**

支出の追加時はミッションやバッジが更新されますが、編集・削除では主に月次集計だけが更新されます。記録日やカテゴリを変更した場合、ミッション、バッジ、ストリークと実データがズレる可能性があります。

**修正方針**

- 支出・自炊・節約記録の追加/編集/削除後に、派生データを再計算する仕組みを作る。
- ミッションの進捗をイベント加算方式だけにせず、必要なものは現在の記録から再集計する。
- 編集や削除で過去の達成履歴を取り消すかどうかは仕様として決める。

**修正後の状態**

- 記録を修正しても、ホーム、統計、ミッション、バッジの表示が整合する。
- 後から入力ミスを直しても、状態が壊れにくい。

**関連ファイル**

- `mobile/src/store/useAppStore.ts`
- `mobile/app/(tabs)/stats.tsx`

### 10. ストリークのリセット条件が粗い

**問題点**

`resetStreakIfNeeded` はカテゴリが `コンビニ` または `自販機` の場合に、無駄遣いなしと間食なしの両方をリセットします。間食なしは本来 `meal === 'snack'` と連動する方が自然で、カテゴリだけで判定すると意図しないリセットが起きます。

**修正方針**

- 無駄遣いなしの対象カテゴリと、間食なしの対象条件を分ける。
- `resetStreakIfNeeded(category)` ではなく、`category` と `meal` の両方を受け取る。
- どの支出が「無駄遣い」なのか、設定可能にするか固定ルールにするか決める。

**修正後の状態**

- ストリークの意味がユーザーに説明しやすくなる。
- 間食なし記録がカテゴリに引きずられず、食事時間帯に基づいて正しく判定される。

**関連ファイル**

- `mobile/src/store/useAppStore.ts`

### 15. ID生成が `Date.now()` 依存になっている

**問題点**

支出、自炊、節約記録の ID に `Date.now()` を使っています。通常利用では衝突しにくいですが、同一ミリ秒で複数登録されると ID が重複する可能性があります。

**修正方針**

- `crypto.randomUUID()` 相当の UUID を使う。
- Expo / React Native で安全に使える UUID 生成方法を導入する。
- 型を `number` から `string` に変える場合は、既存データの migration を用意する。

**修正後の状態**

- 記録IDの衝突リスクが下がる。
- 編集・削除対象を安定して特定できる。

**関連ファイル**

- `mobile/src/types/index.ts`
- `mobile/src/store/useAppStore.ts`

### 16. 未来日付の記録が可能

**問題点**

日付カレンダーでは未来日も選択できます。予定入力として使う意図がなければ、未来の支出や自炊記録がホーム・統計・ミッションに影響する可能性があります。

**修正方針**

- 未来日を選択不可にする。
- もしくは保存時に「未来日ですが記録しますか？」の確認を出す。
- 未来日を許可するなら、ミッションや当月集計にどう反映するかを仕様化する。

**修正後の状態**

- 誤って未来日に保存する事故を防げる。
- ミッションや統計の集計対象が明確になる。

**関連ファイル**

- `mobile/src/components/DateSelector.tsx`
- `mobile/src/components/InputModal.tsx`

### 29. 予算計算 helper の意味が現在の仕様とズレている

### 30. `CircularProgress` の percent 下限 clamp がない

**問題点**

`CircularProgress` は `Math.min(percent, 100)` で上限は制限していますが、下限は制限していません。現状の呼び出しでは大きな問題になりにくいものの、共通コンポーネントとしては負値に弱いです。

**修正方針**

- `const clampedPercent = Math.max(0, Math.min(percent, 100));` を使う。
- 呼び出し側でも負値が入らないようにする。

**修正後の状態**

- 共通ゲージとして安全に使える。
- 将来の画面追加時に予期しない描画崩れを防げる。

**関連ファイル**

- `mobile/src/components/CircularProgress.tsx`
