# DDD スターター

個人開発において、新機能の「価値」と「守るべきルール」を整理するためのワークフロー。

> 参照: `.Codex/skills/ddd-starter/references/ddd-guide.md`

---

## Step 1: アプリの「約束」を確認する

まずユーザーから以下を聞き出す（引数で与えられている場合はそれを使う）：

- 作りたい機能や解決したい課題
- このアプリ（または機能）がユーザーに何を約束するのか

**1文で言えない場合は絞り込みを手伝う。**

---

## Step 2: 7つのセクションで整理する

以下の7セクションを順番に埋めて出力する。

### 【1】この機能が守る価値

このアプリ（機能）がユーザーに約束することを1文で書く。

```
例: 予約の二重確定を防ぎ、安心して予約できる体験を提供する
```

### 【2】登場する重要な言葉（ユビキタス言語）

この機能で使う言葉を列挙する。似た言葉は1つに絞る。

```
例:
- 仮予約
- 確定予約
- キャンセル
- 予約枠
- 在庫引当
```

### 【3】主役の概念

- **Entity**（識別子を持ち状態が変わるもの）:
- **Value Object**（値そのものに意味があるもの）:
- **Aggregate**（整合性を守る単位）:

### 【4】守るべきルール（不変条件）

**「何ができるか」より「何を許してはいけないか」を先に書く。**

```
例:
- 確定済み予約は期限後キャンセル不可
- 在庫引当前は注文確定不可
- 同一ユーザーの同一時間帯での二重予約は不可
```

### 【5】やらないこと（境界の明確化）

この機能では含めない範囲を明示する。

```
例:
- 決済処理は含めない（外部サービスに任せる）
- 通知機能は別フェーズ
- 分析・レポートは今回のスコープ外
```

### 【6】最小リリース単位

「まず何だけ出すか」を1〜2文で書く。

```
例: まず「予約確定の正しさ（二重確定防止）」だけを実装し、キャンセル処理は次フェーズにする
```

### 【7】コアドメイン分類

| 分類 | 該当する機能・概念 |
|------|-------------------|
| コアドメイン（ここに集中） | |
| 支援ドメイン（必要だが差別化ではない） | |
| 汎用ドメイン（外部や既製品に任せる） | |

---

## Step 3: アンチパターンチェック

以下の典型的な失敗がないか確認し、該当するものがあれば指摘する。

| チェック項目 | 状態 |
|------------|------|
| コアと周辺を分けているか | |
| テーブル設計ではなく「守る存在か」で概念を定義しているか | |
| ルールがApplication Serviceではなくドメインモデルに入っているか | |
| 用語が統一されているか（「予約」「申込」「確定」が混在していないか） | |

---

## Step 4: 次のアクション提案

整理した内容をもとに、次のステップを提案する。

1. モデルをコードで表現する（Entity/Value Object の定義）
2. 不変条件をドメインモデルのメソッドに閉じ込める
3. 最小リリース単位を実装する

---

## 出力フォーマット

マークダウンで整理した結果を出力する。各セクションのタイトルを明示し、具体的な例を交えながら埋める。抽象的な回答は避け、ユーザーの機能に即した言葉で書く。
