# 要件定義 スキル

DDD（ドメイン駆動設計）を主軸に、システム全体の要件定義書をユーザーとの対話で作成するワークフロー。

## ファイル責務

| ファイル | 責務 |
|--------|------|
| **SKILL.md**（このファイル） | 5ステップ実行ワークフロー・ヒアリング設計・出力セクション骨格 |
| **references/requirements-guide.md** | 10セクションの詳細テンプレート・DDD理論・記述例・非機能要件目安値 |
| **references/security-checklist.md** | 認証パターン別チェックリスト・法的コンプライアンス判定・セキュリティ要件テンプレート文 |

> 詳細テンプレート・DDD理論・記述例は `references/requirements-guide.md` を参照。
> セキュリティ設計の詳細は `references/security-checklist.md` を参照（Step 4 で読み込む）。

**関連スキル**: 機能単位のDDD設計は `ddd-starter` スキルを使用。このスキルはシステム全体の要件定義を扱い、`ddd-starter` の出力を入力として受け取ることも可能。

---

## Step 1: 基本情報の確認

引数またはコンテキストから以下の項目が揃っているかを確認する。

| 必須項目 | 内容 |
|---------|------|
| アプリ/システム概要 | どんなシステムか（1〜2文） |
| 解決する課題 | 誰の・何の問題を解決するか |
| 開発規模 | 個人開発 / チーム開発 / 受託開発 |

**3項目すべて揃っている場合**: Step 2 へ直進（追加質問不要）。

**不明・欠落がある場合**: AskUserQuestion（1回・最大3項目）で不足項目のみ補完する。

---

## Step 2: ドメイン・ユーザーの把握

AskUserQuestion を1回使い、最大4項目をヒアリングする。

1. ターゲットユーザー・ペルソナ（具体的な人物像）
2. このシステムの核心的な価値（1文で言うと？）
3. コアドメイン候補（業務の核になるもの・競合他社にマネできない部分）
4. MVPスコープ（最初にリリースする最小機能セット）

**絞り込みロジック**: 「全員」「みんな」という答えが来たら「最初に使ってもらいたい人は誰か？」と絞り込む。

---

## Step 3: 技術スタック・非機能要件の確認

AskUserQuestion を1回使い、最大4項目をヒアリングする（「未定」可）。

1. 技術スタック（フロント / バック / DB / インフラ）
2. 非機能要件（レスポンス目標・同時接続数の目安）
3. 想定ユーザー規模（リリース時 / 1年後 / スケーラビリティ要件）
4. 成功指標（KPI）・目標値・評価期限（例: 7日継続率40%以上 / DAU100人 / TBD可）

「未定」「わからない」は **TBD** として記録して次へ進む。

> **KPI出典の記録**: Step 5の出力時に、各KPI項目がユーザー回答か仮置きかを `（ユーザー回答）` / `（仮置き・要確認）` で明示する。データ保持・バックアップ方針は Step 4 の2回目でまとめて確認する。

---

## Step 4: セキュリティ・スコープの確認

`references/security-checklist.md` を参照しながらヒアリングする。

### 1回目（必須）: AskUserQuestion・最大4項目

1. 認証方式（メール/パスワード・SNSログイン・パスワードレス・認証なし）
2. 権限管理・ロール設計（管理者/一般ユーザー等の区分）
3. 取り扱うセンシティブデータの種類（個人情報・医療・金融・なし）
4. 法的コンプライアンス要件（個人情報保護法・GDPR・HIPAA等 / 不明 / 不要）

### 2回目（必要な場合）: AskUserQuestion・最大4項目

1. やらないこと（スコープ外として明示したい範囲）
2. 将来フェーズに回す機能
3. 外部サービスに委譲する領域（認証・決済・通知等）
4. データ保持・バックアップ方針（Step 3で未確定の場合のみ）

### セキュリティベースラインの確認

`references/security-checklist.md` のセクション6（セキュリティレビューチェックリスト）を参照し、以下の最低限の基礎項目を確定させる。未確定の場合はTBDとして記録し、セクション8に「実装時確認が必要な項目」として明示する。

- **通信/API防御**: CORS設定・レートリミット・セキュリティヘッダーの方針
- **秘密情報管理**: APIキー・環境変数の管理方法（コードにハードコードしないか）
- **監査ログ/インシデント対応**: ログ保持期間・データ侵害時の通知方針

> **Step 4の完了条件**: `security-checklist.md` セクション6の全項目がYES/NO/TBDのいずれかで埋まっていること。

### 条件分岐

- **センシティブデータ（医療・金融・個人情報）が含まれる** → `security-checklist.md` の該当セクションを参照して追加ヒアリング
- **規模「1万人以上」またはグローバル展開** → スケーラビリティ・CDN・マルチリージョン要件を確認
- **TBD が3項目以上** → 要件定義書に「前提確認事項」セクションを追加

---

## Step 5: 要件定義書の生成・出力

`references/requirements-guide.md` の詳細テンプレートを参照して、以下の10セクションで要件定義書を出力する。

### 出力セクション

1. **プロジェクト概要**（背景・目的・提供価値・開発規模）
2. **ユーザー・ステークホルダー**（ペルソナ・利害関係者）
3. **ユビキタス言語**（用語統一・似た言葉の整理・用語集）
4. **ドメインモデル**（Entity / Value Object / Aggregate / 不変条件）
5. **機能要件**（コア/支援/汎用ドメイン分類・MVPフラグ付き）
6. **非機能要件**（パフォーマンス・可用性・スケーラビリティ・保守性）
7. **技術スタック**（採用技術の選定理由・TBD含む）
8. **セキュリティ設計**（認証・認可・データ保護・コンプライアンス）
9. **スコープ管理**（やること・やらないこと・将来フェーズ）
10. **受け入れ基準**（数値KPI・完了条件）

### 出力セクション（条件追加）

- **TBD が3項目以上の場合**: セクション10の後に「**11. 前提確認事項**」を追加し、TBD項目と確認方法・責任者をリスト化する。

### 出力後のアクション

- TBD 項目を「11. 前提確認事項」または「**次のアクション**」の一方にまとめる（重複不要）
- ファイル保存を提案する（例: `docs/requirements.md`）
- ユーザーが保存を希望した場合は Write ツールでファイルとして保存する

---

## 出力フォーマット

- マークダウン形式で会話内に表示する
- 各セクションは具体的な言葉で記述する（「TBD」は未確定項目のみに限定）
- ユーザーのシステムに即した言葉を使う（汎用的な表現を避ける）
- 抽象的な回答より、具体例・数値・対象ユーザー名を使う
