# 要件定義書作成ガイド

DDD（ドメイン駆動設計）アプローチによる要件定義書作成の詳細リファレンス。

---

## 1. 要件定義のプロセス（DDDアプローチ）

```
アイデア/課題
    ↓
ユビキタス言語の特定（共通言語の確立）
    ↓
ドメインモデルの設計（Entity/Value Object/Aggregate）
    ↓
機能要件への落とし込み（コア/支援/汎用分類）
    ↓
非機能要件・セキュリティ・スコープの確定
    ↓
受け入れ基準の数値化
```

**DDDが要件定義に有効な理由**: ビジネスの「守るべきルール（不変条件）」を先に定めることで、後工程での仕様ブレを防ぐ。

---

## 2. DDD観点での要件整理

### コアドメイン・支援ドメイン・汎用ドメインの分類

| 分類 | 定義 | 開発方針 |
|------|------|---------|
| **コアドメイン** | ビジネスの核心・競合他社にマネできない部分 | 自社で最高品質を実装する |
| **支援ドメイン** | 必要だが差別化にならない機能 | シンプルに実装、外注も検討 |
| **汎用ドメイン** | どの会社でも同じ仕組みの機能 | 外部サービス・ライブラリに委譲 |

**例（食材管理アプリ）:**
- コアドメイン: 冷蔵庫在庫の状態管理・廃棄予測アルゴリズム
- 支援ドメイン: ユーザープロファイル管理・通知設定
- 汎用ドメイン: メール認証（Auth0等）、プッシュ通知（FCM等）

### ユビキタス言語の作り方

**目的**: 開発者・ビジネス担当・ユーザーが同じ言葉を使う状態を作る。

**手順:**
1. ヒアリングで出てきた言葉をすべて列挙する
2. 似た言葉（「予約」「申込」「確定」等）を1つに絞る
3. 略称・口語は正式名称に統一する
4. 用語集として定義文を付ける

**例（医療予約システム）:**

| 用語 | 定義 | 使わない言葉 |
|------|------|------------|
| 診療予約 | 患者が医師の診療枠を確保すること | 申込、予約登録 |
| 診療枠 | 医師が提供できる時間スロット | スロット、空き時間 |
| キャンセル | 確定済み予約を取り消すこと | 取消、削除 |

### ドメインモデルの要素

```
Entity（識別子を持ち、状態が変化するもの）
  例: 注文、ユーザー、商品

Value Object（値そのものに意味があり、同一性を識別子で管理しないもの）
  例: 金額、住所、メールアドレス

Aggregate（整合性を保つ単位。1つのトランザクションで変更される境界）
  例: 注文（注文明細を含む）、ユーザー（プロファイルを含む）

不変条件（Aggregate が常に守るべきルール）
  例: 確定済み注文は期限後キャンセル不可
      在庫がゼロの商品は注文確定不可
```

## 3. 10セクションの完全テンプレート（記述例付き）

### セクション1: プロジェクト概要

```markdown
## 1. プロジェクト概要

### 背景
[なぜこのシステムが必要か。解決する課題の現状を書く]
例: 一人暮らしの社会人が食材の廃棄を減らせずにいる。
    冷蔵庫内の在庫を把握できず、同じ食材を買ってしまう問題が発生している。

### 目的
[このシステムで何を達成するか。動詞で書く]
例: 冷蔵庫内の食材をリアルタイムで把握し、廃棄を月30%削減する。

### 提供価値
[ユーザーが得られる具体的なメリット]
例: 「レシートを撮るだけで食材リストが自動作成され、今夜使える食材が即座にわかる」

### 開発規模
- 開発体制: 個人開発 / 2名チーム / 5名チーム
- リリース目標: 2024年Q2
- フェーズ: MVP（Phase 1） → 正式版（Phase 2）
```

### セクション3: ユビキタス言語

```markdown
## 3. ユビキタス言語（用語集）

| 用語 | 定義 | 使わない言葉 |
|------|------|------------|
| 食材 | 冷蔵庫に保存している食べ物の一品 | アイテム、食品 |
| 賞味期限 | 食材の品質が保証される最終日 | 期限日、消費期限（区別して使う） |
| 食材登録 | 冷蔵庫に食材を追加する操作 | 追加、入力、登録 |
| 廃棄 | 期限切れにより食材を処分すること | 捨てる、削除 |

> ⚠️ 似た言葉の整理: 「削除」は操作（ユーザーが手動で消す）、「廃棄」はビジネス事象（期限切れ）として区別する。
```

### セクション4: ドメインモデル

```markdown
## 4. ドメインモデル

### Entity
- **食材 (Ingredient)**: 食材ID・名称・数量・賞味期限・保存場所
- **ユーザー (User)**: ユーザーID・メールアドレス・登録日

### Value Object
- **賞味期限 (ExpiryDate)**: 日付値・残日数の計算メソッド
- **数量 (Quantity)**: 数値・単位（個/ml/g）

### Aggregate
- **冷蔵庫 (Refrigerator)** [Aggregate Root]:
  - 含む: 食材リスト
  - 不変条件:
    - 同じ食材名・同じ賞味期限は重複登録不可
    - 数量はゼロ以上の値のみ許可

### 不変条件（ビジネスルール）

> ⚠️ **DDDの原則**: 不変条件はAggregate内部の整合性ルールのみを書く。「誰がアクセスできるか」の認可ルールは不変条件ではなく、セクション8（セキュリティ設計・RBAC）に記述する。

1. 賞味期限が切れた食材は「廃棄済み」状態に自動遷移し、削除はできない（履歴保持）
2. 食材の数量を負にすることはできない
```

### セクション8: セキュリティ設計

```markdown
## 8. セキュリティ設計

### 認証・認可
- 認証方式: JWT（Supabase Auth発行）
- セッション有効期限: 24時間
- リフレッシュトークン: 30日間
- ロール: 一般ユーザー / 管理者

### 認可設計（RBAC）
| リソース | 一般ユーザー | 管理者 |
|---------|------------|--------|
| 自分の食材 | CRUD | CRUD |
| 他ユーザーの食材 | 不可 | 読み取り（サポート目的） |
| ユーザー管理 | 不可 | CRUD |

### データ保護
- 通信: HTTPS必須（TLS 1.3）
- パスワード: bcrypt（ソルト付きハッシュ）
- センシティブデータの暗号化: なし（今フェーズ）
- 個人情報の保存: 最小限（メールアドレス・表示名のみ）

### コンプライアンス
- 個人情報保護法: 適用（プライバシーポリシー・同意フロー必要）
- GDPR: 対象外（日本国内ユーザーのみ）
```

## 5. MVPスコープの切り方

### やらないことリストの作り方

**原則**: 「あったら便利」はすべてやらないことリストに入れる。

1. アイデア段階で挙がった全機能を列挙する
2. 「なければリリースできないか？」でフィルタする
3. NOならスコープ外。「将来フェーズ」に記録する

**MVPの評価基準:**
- ユーザーが初めて使った瞬間に「価値を感じられるか」
- コアリスク（技術的不確実性）が解消できているか
- 1人のターゲットユーザーが1つの課題を解決できるか

### スコープ外の記録方法

```markdown
| 機能 | 除外理由 | 将来フェーズ |
|------|---------|------------|
| レシピ提案 | コアバリューではない・実装工数大 | Phase 2 |
| グループ共有 | ターゲットは個人ユーザー | Phase 3 |
| 分析グラフ | データが溜まってから意味を持つ | Phase 2 |
```
