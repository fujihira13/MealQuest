# セキュリティ要件チェックリスト

要件定義のStep 4で参照するセキュリティ設計ガイド。認証・認可・データ保護・コンプライアンス要件のヒアリング支援と、セクション8への貼り付け用テンプレート文を提供する。

---

## 1. 認証・認可

### 認証方式の選択基準

| 方式 | 適合ケース | 実装コスト | セキュリティ強度 |
|------|----------|-----------|---------------|
| メール/パスワード | 基本的なWebアプリ | 低 | 中（適切なハッシュ化必須） |
| SNSログイン（OAuth） | 個人ユーザー向けアプリ | 低〜中 | 高（プロバイダーに委譲） |
| パスワードレス（マジックリンク） | ユーザー体験重視 | 中 | 高（フィッシング耐性） |
| SAML/SSO | 企業・エンタープライズ | 高 | 非常に高 |
| 多要素認証（MFA） | 機密情報を扱うシステム | 中 | 非常に高 |
| 認証なし | 公開情報のみ・内部ツール | なし | ― |

**推奨ライブラリ/サービス:**
- 個人開発: Supabase Auth / Firebase Auth / Auth0（無料枠あり）
- エンタープライズ: Auth0 / Okta / AWS Cognito

### RBAC（ロールベースアクセス制御）設計パターン

**シンプル2ロール（推奨: MVP）:**
```
一般ユーザー: 自分のデータのCRUD
管理者: 全データの読み取り + ユーザー管理
```

**3ロール構成（支援が必要なサービス向け）:**
```
一般ユーザー: 自分のデータのCRUD
サポートスタッフ: 全データの読み取り（サポート目的）
管理者: 全操作 + 設定変更
```

**多階層ロール（エンタープライズ向け）:**
```
閲覧者 < 編集者 < 承認者 < 管理者 < スーパー管理者
```

### 認可チェックリスト

- [ ] 自分のリソースと他者のリソースを区別しているか
- [ ] APIエンドポイント単位で認可チェックをしているか（フロントエンドのUIのみで制御しない）
- [ ] 管理者機能は別エンドポイントまたはミドルウェアで保護しているか
- [ ] Row Level Security（DB層での認可）を使用するか

## 2. データ保護

### センシティブデータ分類表

| データ種別 | 例 | 保護レベル | 暗号化要否 |
|----------|----|---------|---------|
| 一般個人情報 | 氏名・メールアドレス | 高 | 転送中は必須・保存中は推奨 |
| 医療情報 | 診断・処方・検査結果 | 最高 | 必須（保存中・転送中） |
| 金融情報 | クレジットカード・銀行口座 | 最高 | 必須（PCI DSS準拠） |
| 認証情報 | パスワード・トークン | 最高 | ハッシュ化必須（平文保存禁止） |
| 位置情報 | GPS・住所 | 高 | 転送中は必須 |
| 行動履歴 | 閲覧履歴・操作ログ | 中 | 転送中は必須 |
| 公開情報 | ユーザー名（公開設定） | 低 | 転送中は必須 |

### 個人情報の最小化原則

```
収集する情報は「必要最小限」に限定する。
× 生年月日（年齢確認が不要なのに収集）
○ メールアドレスのみ（認証に必要な最小情報）
```

### 暗号化チェックリスト

- [ ] パスワードはbcrypt/argon2でハッシュ化（平文・MD5・SHA-1は禁止）
- [ ] 通信はTLS 1.2以上（1.3推奨）
- [ ] 医療・金融データは保存時にも暗号化（AES-256等）
- [ ] 暗号化キーはコードと分離して管理（環境変数・シークレットマネージャー）
- [ ] バックアップデータも暗号化

## 3. 通信セキュリティ

### HTTPS必須化チェックリスト

- [ ] 全エンドポイントでHTTPS強制（HTTP→HTTPSリダイレクト）
- [ ] HSTS（HTTP Strict Transport Security）ヘッダーを設定
- [ ] 証明書の有効期限を監視・自動更新（Let's Encrypt等）
- [ ] 混在コンテンツ（Mixed Content）なし

### APIセキュリティチェックリスト

- [ ] 認証トークンはAuthorizationヘッダーで送信（URLパラメータ禁止）
- [ ] CORS設定: 許可オリジンを明示的に指定（`*`は禁止）
- [ ] レートリミット設定（ブルートフォース防止）
- [ ] 入力値バリデーション（SQLインジェクション・XSS防止）
- [ ] エラーレスポンスにスタックトレースを含めない
- [ ] APIキーのローテーション方針

### セキュリティヘッダー設定

```
Content-Security-Policy: default-src 'self'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
```

## 4. 法的コンプライアンス

### 個人情報保護法（日本）適用判定

**適用条件**: 個人を特定できる情報（氏名・メールアドレス・IPアドレス等）を収集する場合

**必要な対応:**
- [ ] プライバシーポリシーの作成・公開
- [ ] 収集目的の明示と同意取得フロー
- [ ] 情報開示・訂正・削除の対応窓口
- [ ] データ保持期間の設定と削除ポリシー
- [ ] 第三者提供の制限（同意なき第三者提供禁止）

### GDPR（EU一般データ保護規則）適用判定

**適用条件**: EU在住ユーザーのデータを収集・処理する場合（国内企業でも適用）

**判定フローチャート:**
```
EUユーザーへのサービス提供を想定している？
  ↓ YES
GDPR適用 → 以下が必要:
  - データ処理の法的根拠の特定（同意/正当な利益等）
  - データ主体の権利対応（アクセス権・忘れられる権利等）
  - データ保護責任者（DPO）の検討
  - データ侵害時の72時間以内の報告義務
  ↓ NO
GDPR適用外（個人情報保護法のみ適用）
```

### 医療情報（HIPAA等）の特別要件

**適用条件**: 医療記録・診断・処方・健康状態等を扱う場合

**必要な対応（日本）:**
- [ ] 医療情報の安全管理ガイドライン（厚生労働省）への準拠
- [ ] アクセスログの保管（最低6年間）
- [ ] 医療情報の第三者提供制限
- [ ] 患者本人への情報開示手続き

**HIPAA（米国ユーザーを含む場合）:**
- [ ] 保護された医療情報（PHI）の暗号化
- [ ] Business Associate Agreement（BAA）の締結
- [ ] 監査ログの保管（最低6年間）

### 金融情報の特別要件（PCI DSS）

**適用条件**: クレジットカード情報を自社サーバーで処理・保存する場合

**推奨**: カード情報は自社で保持せず、Stripe/PayPal等の決済代行サービスに委譲する。

**委譲できない場合:**
- [ ] PCI DSS準拠の認定取得（高コスト）
- [ ] カード番号のトークナイゼーション
- [ ] 定期的な脆弱性スキャン

## 5. セキュリティ要件テンプレート文（セクション8貼り付け用）

### パターンA: 個人開発・メール認証・センシティブデータなし

```markdown
## 8. セキュリティ設計

### 認証・認可
- 認証方式: メール/パスワード（bcryptハッシュ化）
- セッション: JWTトークン（24時間有効）
- ロール: 一般ユーザー / 管理者（2ロール構成）

### 認可方針
- ユーザーは自分のリソースのみCRUD可能
- 管理者は全ユーザーデータの読み取り可能

### データ保護
- 通信: HTTPS（TLS 1.3）必須
- パスワード: bcrypt（コスト係数12）
- 個人情報: メールアドレス・表示名のみ収集（最小化）

### コンプライアンス
- 個人情報保護法: 適用（プライバシーポリシー作成・同意フロー実装）
- GDPR: 対象外（日本国内ユーザーのみ）

### セキュリティ対策
- レートリミット: ログイン試行10回/分まで
- CORS: 許可オリジンを明示的に設定
- セキュリティヘッダー: CSP・X-Frame-Options等を設定
```

### パターンB: SNSログイン・OAuth

```markdown
## 8. セキュリティ設計

### 認証・認可
- 認証方式: Google OAuth 2.0 / Apple Sign In
- セッション: JWTトークン（Supabase Auth発行・1時間有効）
- リフレッシュトークン: 30日間
- ロール: 一般ユーザー / 管理者

### データ保護
- 通信: HTTPS（TLS 1.3）必須
- パスワード: なし（OAuth委譲のため不要）
- 個人情報: OAuthプロバイダーから取得した最小情報（メール・表示名）

### コンプライアンス
- 個人情報保護法: 適用
- OAuthプロバイダーのポリシー: Google API利用規約・Apple Human Interface Guidelines 準拠
```

### パターンC: 医療・金融・高セキュリティ要件

```markdown
## 8. セキュリティ設計

### 認証・認可
- 認証方式: メール/パスワード + MFA（TOTP）
- セッション: JWTトークン（1時間有効・操作ない場合は30分で失効）
- ロール: 患者 / 医師 / 管理者（3ロール構成）
- Row Level Security: Supabase RLSでDB層でも認可制御

### データ保護
- 通信: HTTPS（TLS 1.3）必須
- 保存データ暗号化: AES-256（センシティブデータのカラム暗号化）
- 個人情報最小化: 診療に必要な情報のみ収集

### アクセスログ
- 全操作のアクセスログを6年間保持
- ログへのアクセスは管理者のみ

### コンプライアンス
- 個人情報保護法: 適用（要配慮個人情報として厳格管理）
- 医療情報安全管理ガイドライン（厚生労働省）: 準拠
- HIPAA: [米国ユーザー対応の場合、PHI暗号化・BAA締結・監査ログ6年保持]

### インシデント対応
- データ侵害発生時: 72時間以内に監督機関への報告
- 影響ユーザーへの速やかな通知
- インシデント対応手順書の整備
```

### パターンD: 認証なし（公開情報・内部ツール）

```markdown
## 8. セキュリティ設計

### 認証
- 認証: なし（公開情報のみ提供）
- または: 社内IPアドレス制限（VPN必須）

### データ保護
- 通信: HTTPS（TLS 1.3）必須
- センシティブデータ: 収集・保存しない

### その他
- レートリミット: API乱用防止のため1000回/時間まで
- SQLインジェクション・XSS対策: フレームワーク標準機能で対応
```

## 6. セキュリティレビューチェックリスト

実装前に確認する最低限のセキュリティ設計チェック。

### 認証・認可
- [ ] 認証なしでアクセスできるエンドポイントを意図的に設計したか
- [ ] 認可バイパス（権限昇格）のリスクを検討したか
- [ ] セッションの無効化（ログアウト）処理を実装するか

### データ
- [ ] 不要な個人情報を収集していないか
- [ ] データ保持期間と削除ポリシーを決めたか
- [ ] バックアップデータのアクセス制限を決めたか

### 通信
- [ ] 全エンドポイントがHTTPS強制か
- [ ] 内部サービス間の通信も暗号化するか

### コード品質
- [ ] 環境変数・秘密鍵をコードにハードコードしていないか
- [ ] エラーメッセージに内部情報を含めないか
- [ ] 依存パッケージの脆弱性チェック方法を決めたか
